## Sheet 1 — word validation · required · ~45–75 min

**One question per row, and it is not a reading task:**

> Is this a real, well-formed Hindi word as written? **yes / no / unsure**

Fill `is_real_wellformed_hindi_word` with exactly `yes`, `no` or `unsure`. `reader_note` is free
text and optional — a note like "Marathi, not Hindi" or "looks like a misreading of X" is useful
but never required.

`no` and `unsure` words are dropped from the pool and the battery is rebuilt deterministically, at
zero cost.

**Why this matters.** The whole autocorrection hypothesis depends on the base being a plausible
real word: a model only autocorrects *toward* something. If an annotation was itself a misreading,
the "word" may be a non-word, and an item built on it does not test what we think it tests.

**Word ids are stable** — `w-<12 hex of sha256(NFC(word))>` — so an answer collected today still
matches its word after the list is expanded. That will happen: the battery needs 84–90 words to
bring the iid reference calculation below 5%, and after validation the pool holds **48 accepted
words**.

## Sheet 2 — perceptibility · recommended · ~20 min

Each row names **two images**. The reader is not told which is which and is **not asked to read
either one**:

> Can you see a difference between these two images? **yes / no / only when I look closely**

Fill `can_you_see_a_difference` with `yes`, `no` or `close`.

**Why this matters.** The build proves mechanically that two strings produce different final
pixels. It does **not** prove a person can *see* the difference at 40 point — a nukta dot or an
anusvara is small. A class where readers routinely answer `no` should be reported separately or
dropped, for the same reason the invisible nukta pair was rejected: scoring a checker on a
difference people cannot see is not a fair test.

**Sampling is deterministic**: round-robin across the five failure groups, hard opportunities
first, 25 pairs. The `is_hard_opportunity` column is included so a `no` answer on a hard item is
immediately visible — that is the case that would matter most.

⚠️ **This produces no ground truth.** It tunes item difficulty. A wrong answer changes an item's
stratum, never its verdict.

## Sheet 3 — rendering sanity check · required · ~10 min

20 clean renders, sampled evenly.

> Does this look like normal, correctly formed Hindi text? **yes / no**

Fill `looks_like_normal_hindi_text` with `yes` or `no`; use `reader_note` for anything odd.

**Why this matters.** If the pinned font renders badly — missing marks, broken conjuncts, tofu
boxes — we would be testing checkers against a broken instrument and calling the result a checker
finding. Ten minutes rules that out. It checks the tool, not the reader.

## What is deliberately NOT here

- **No source-image transcription task.** Nobody looks at a photograph and says what it says. That
  was EVAL-004, and constructing the images is what removed it.
- **No second reader.** One competent reader suffices because **none of these three tasks produces
  ground truth** — the answer key comes from construction. A mistake here degrades the battery; it
  cannot corrupt the answers. If the Controller prefers two readers on sheet 1 for robustness that
  is a reasonable belt-and-braces choice, but it is optional here where it was structural before.
- **No Class B malformed-glyph judgement.** That genuinely needs human judgement and it is not
  part of this pack. See `../GENERATED-GLYPH-STRESS-LAYER.md`.
