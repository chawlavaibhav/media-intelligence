# Final Pre-Execution Freeze Program

**Date:** 26 Aug 2026  
**Status:** ACTIVE — Controller-assigned, cloud-safe, ₹0 external spend  
**Purpose:** convert the completed macro research into the exact executable package required before any paid current-model testing.

## 1. Program objective

The discovery phase is complete enough. This tranche does **not** reopen broad research.

It must jointly produce the smallest defensible package that lets the Controller answer:

1. What customer request shapes does the first product represent?
2. What capabilities and production conditions must the lab measure?
3. What benchmark and evaluator architecture will measure them without a cartesian explosion?
4. What persistence/resource structure is required before the first real generation is made?
5. Which models constitute the scientific Wave-1 candidate roster, independent of access?
6. Through which exact version-pinned routes can those models be called, at what current prices?
7. What generation, evaluator, human-review and resource cost does the first empirical wave imply?

No paid execution is authorised by this program.

## 3. Frozen principles carried into this tranche

- Normalized Request preserves what the customer asked.
- Creative IR remains model/provider independent.
- Requested operation and production workflow mode are distinct.
- Creative IR / Production Requirement Profile / Production IR remain separate layers.
- Capability Registry stores empirical evidence, never routing scores.
- Canon does not select models.
- One provider/API/transform call = one trial.
- Outcome cost is whole-journey CpAO; fully-loaded CpAO is primary and API/tool CpAO is diagnostic.
- No single synthetic complexity score.
- Benchmark design is sparse/adaptive, not a cartesian product.
- Discovery-source lineage and benchmark lineage remain separate.
- The original 30 briefs stay byte-identical.
- Historical 36-capability and 100-item artifacts remain preserved as V1 baselines even where V2 supersedes them.

## 4. Four parallel programs

### CANON-010 — Request Contract & Coverage Freeze

Owns the customer-request side only.

Must produce:
- Media Request Grammar v1 proposal ready for Controller freeze;
- exact Normalized Request field additions, including requested operation, supplied-asset mutation intent, output cardinality/set semantics, specification-vs-omission provenance and camera-vs-subject motion distinction;
- explicit deferral boundary for multi-turn history;
- a request-coverage extension bank covering at minimum edit-supplied-asset, animate-supplied-image and variant/campaign-set jobs;
- machine-readable mapping from every extension item to request grammar features and required acceptance semantics;
- proof the original 30-bank is unchanged;
- a coverage report showing what the combined old+extension bank now covers and still does not cover.

No provider/model/workflow decisions. No Production IR.

### EVAL-009 — Measurement & Benchmark Freeze

Owns measurement architecture, not provider sourcing.

Must produce:
- Capability Contract v2 proposal with exact V1→V2 mapping and backward-compatibility semantics;
- dependency/prerequisite contract including `blocked_by_prerequisite_failure` semantics;
- condition/envelope contract;
- Production Requirement Profile shape, provider/model agnostic;
- benchmark v2 architecture and exact runnable Wave-1 item/call structure;
- evaluator-family map and qualification requirements for every active Wave-1 capability;
- scientific Wave-1 model/workflow roster chosen for information value **without using access-route availability as an admission criterion**;
- generation/evaluator/human call-count forecast with prices left as external inputs where not officially verified.

It must challenge EVAL-008 rather than inherit it mechanically. Any candidate whose justification is only leaderboard position, vendor novelty, geography/training-lineage speculation or an unverified marketing claim must be demoted unless a concrete product-relevant hypothesis is stated.

The unsupported/~99% Hindi/Bengali character-accuracy claim in EVAL-008 must not be load-bearing unless primary evidence is found.

No paid calls. No Registry population.

### RES-004 — Production Evidence & Persistence Readiness

Owns execution evidence, lineage, packs and cost persistence.

Must produce:
- outcome/production-topology v3 implementation-ready schema and validators;
- explicit compatibility with v2.1 without rewriting historical archives;
- ordered multi-parent artifact lineage and deterministic local-step semantics;
- whole-outcome CpAO recomputation contract supporting API/tool and fully-loaded views;
- exact minimum controlled-pack requirements implied by the accepted architecture direction, with unresolved quantities clearly parameterised against EVAL-009 where necessary;
- legitimate acquisition/capture route plan and rights gates, but **no acquisition**;
- human-review/annotation effort inputs needed for the final budget;
- fail-closed fixtures for lineage cycles, unknown parents, invented trials, double-counted cost and historical backfill.

No creative labels, Eval thresholds, provider selection or acquisition spend.

### EVAL-010 — Model Route / Version / Price Verification

Owns supply verification only. It does **not** choose the scientific model roster.

Start from the EVAL-008 candidate universe and verify every potentially Wave-1-relevant row using current first-party/provider-authorised evidence wherever possible.

Required order for sourcing:
1. Frontier Clouds, if the exact service can be identified from supplied/public evidence;
2. fal;
3. direct vendor or another legitimate production API.

For each exact selected version/workflow, verify or explicitly leave unresolved:
- model identity and version/pinning semantics;
- endpoint/access path;
- supported workflow modes and material controls;
- native duration/resolution/aspect/audio/reference/edit controls;
- billing unit and current price;
- version pinning / floating alias risk;
- aggregator-vs-direct control differences;
- access/account/terms/enterprise gating.

Search snippets may be leads but **may not populate execution-grade price/version fields**. Those fields require a primary/provider-authorised source. Unknown remains null.

Produce a machine-readable budget-input table containing only verified pricing units and an account/action checklist. If Frontier Clouds remains unidentified, return the completed 26-row verification checklist and leave that route unresolved rather than guessing.

No API/model calls, account creation, terms acceptance or spend.
