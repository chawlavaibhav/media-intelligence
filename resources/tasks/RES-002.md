# Task RES-002: Devanagari calibration material + transient large-source acquisition

**TASK ID:** RES-002

**OBJECTIVE:** Unblock Eval's Hindi/Devanagari checker work by acquiring suitable public recognition material, and prove a low-retention acquisition method for large, easy-to-reacquire public datasets so we keep reproducibility metadata and a useful subset rather than storing entire archives long-term.

**WHY WE ARE DOING THIS:** RES-001 produced a useful 4.58 GB mixed corpus, but it contains no known Devanagari/Indic material, so it does not unblock the Hindi-text checker. RES-001 also found at least one valuable source, VideoGen-RewardBench, whose 13.42 GB monolithic archive was too large under the old pilot rule. The human has now approved a different storage principle for such easy-to-reacquire public sources: process them transiently where technically safe, retain only the useful bounded subset plus exact provenance/reproduction metadata, and delete the large temporary payload after validation.

## WORK PACKAGE A — Devanagari checker-calibration material

**Goal:** acquire public, ungated material that can test whether a candidate evaluator can correctly **read** Hindi/Devanagari text before we trust it to judge generated Hindi text.

Assess and, where permitted by `resources/CHARTER.md`, acquire bounded material from the Devanagari/Indic recognition resources already identified by Eval, including as relevant:
- material associated with arXiv:2606.29213 (`Can OCR-VLMs Read Devanagari?`), if publicly released;
- IIIT-ILST;
- IndicSTR12;
- Bharat Scene Text Dataset / other directly relevant public Devanagari scene-text material;
- other already-public recognition resources only when they are clearly in the same source family and improve degraded/real-world coverage.

Requirements:
- use official/creator/lab distribution where available;
- public + ungated + no explicit prohibition may be acquired for bounded internal research/evaluation even if licence is unstated; record rights as `not_stated` / `not_verified` rather than inferring permission;
- no login, form, email approval, click-through terms, paywall, API key, anti-bot evasion or unofficial mirror;
- prefer material with human transcriptions / target strings so Eval has known answers;
- include real/degraded text where available; clean synthetic text alone is insufficient for calibration because published evidence suggests it may not distinguish strong from weak readers;
- do not label any public annotation as project ground truth without Eval/human validation; it is candidate calibration material.

**Deliverable:** a small, well-documented Devanagari calibration-material pool plus source records/manifests that Eval can consume in a later approved task. Do not perform calibration itself.

## WORK PACKAGE B — transient acquisition for large public archives

**Goal:** prove that large, easy-to-reacquire sources can be used without being stored in full long-term.

### First target: VideoGen-RewardBench

RES-001 established that VideoGen-RewardBench is public/ungated, Apache-2.0, valuable for its 12-generator diversity, but distributed as one ~13.42 GB archive.

Use this priority order:

1. **Prefer HTTP range/member-level access or true streaming extraction** if the official host technically supports it. The aim is to transfer/read only the archive portions needed for the selected members while never staging the full archive on disk.
2. If range/member extraction is not feasible, a full temporary download is allowed **only if the 12 GB free-disk floor can still be maintained at every point including extraction**. Do not relax the floor implicitly.
3. If neither is possible, STOP this work package and report the exact technical constraint and temporary disk requirement; do not exceed the floor.

Selection must be deterministic and content-blind. Preserve the source's generator diversity where its metadata makes that possible — e.g. ensure representation across distributor-defined generators rather than simply taking the first N files. Do not invent creative-quality strata.

**Retention principle:** keep only the bounded subset actually needed for future evaluation plus manifests, selected-member IDs/paths, source version, official URL, retrieval script, hashes of retained items, and enough remote metadata to reproduce the selection. Delete the large temporary archive and all non-retained extracted media after successful validation. Log deletions. Re-download later if a future approved task needs more.

### Second large source

After VideoGen-RewardBench, inspect the already-assessed public/ungated sources and identify whether another genuinely large source would benefit from the same transient method. Do **not** assume the advertised size equals accessible media: VideoFeedback is the cautionary case where the card says ~8.81 GB but the currently exposed repo yielded only ~0.18 GB.

Proceed with a second large source only if:
- it is already inside an approved RES source family;
- public/ungated and permitted under the current Resources policy;
- the additional subset fills a real coverage gap rather than adding volume for its own sake;
- the same disk-floor and transient-retention rules can be met.

If no second source meets those conditions, record that rather than forcing one.

## STORAGE / RETENTION POLICY FOR RES-002

- Maintain **at least 12 GB free disk at all times**.
- Existing RES-001 retained corpus may stay unless a later task explicitly approves pruning it.
- New retained media target: **<= 2 GB total across RES-002**, unless Controller approval is requested for more.
- Temporary network transfer may exceed retained bytes, but temporary **disk** staging may not violate the 12 GB floor.

If range/stream access means the full archive was never downloaded, do not fabricate a full-archive hash; record the remote metadata and retained-member hashes instead.
